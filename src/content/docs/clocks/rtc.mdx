The C906 time counter has a dedicated clock control in **MM_MISC**, at `0x30000018`. It is separate from the D0 core clock gate and from the CLINT timer-compare registers.

## Clock and interrupt roles

The counter clock follows the D0 core clock through its divider:

```text
counter rate = D0 core rate / (C906_RTC_DIV + 1)
```

The counter supplies time. A timer compare supplies an event deadline. OpenSBI manages machine timer events and exposes the SBI TIME interface to S-mode software. The register here establishes the counter clock; it does not replace the [CLINT and SBI timer path](/interrupts/local/#timer-delivery).

## Programming sequence

For initialization, disable the counter clock, update the divisor field and enable the clock as required. The counter-reset control is `C906_RTC_RST`. Counter resets and divider changes alter the time base seen by all consumers; initialize this path before those consumers start using it.

`/cpus/timebase-frequency` must describe the resulting counter rate. The property is a description, not a hardware initialization operation.

## Observed enable behavior

On the M1s Dock on 2026-10-21, `CPU_RTC` read as `0x0000000a`: divider encoding 10, reset clear, clock enable clear. Three `time` CSR samples separated by fixed-count instruction loops all returned zero. After writing `0x8000017b` to enable the clock with divider encoding 379, the same bounded probe returned increasing samples: `330982`, `344140`, `396772`.

With the counter running, Linux completed `check_unaligned_access_all_cpus()` and proceeded to its root-filesystem mount. The observation establishes that time advanced with this clock configuration. It does not assign an independently measured absolute frequency to this configuration.

The later power-on and board-RESET comparison again read `CPU_RTC = 0x0000000a`
and `time = 0` at the U-Boot prompt, before any manual clock change. The live
initialization above did not persist across those boots. The same sessions
had a working UART console; console operation did not establish a running
counter. See the [paired boot readbacks](/references/observations/#power-on-and-board-reset-readbacks).

## U-Boot delay dependency

The counter also supplies U-Boot's delay loop. In the tested build,
`get_ticks()` reads the `time` CSR, and `udelay()` waits for that value to
advance. This dependency applies even to a polling operation.

On 2026-10-22, an S-record reception consumed and echoed its S7 terminator
but produced no completion summary or prompt while the counter was stopped.
The `loads` completion path calls `udelay(10000)` before printing the summary;
with a stationary counter, that delay cannot finish. A physical board RESET
was used to recover the stalled session.

After applying the previously tested CPU_RTC configuration, a 1 KiB transfer
completed and its RAM CRC matched the PC file:

| Stage | CPU_RTC readback | Result |
| --- | --- | --- |
| Before initialization | `0x0000000a` | Starting state of the clean run |
| During reception | `0x8000017b` | `loads` completed and RAM CRC was `b70b4c26` |
| After restoration | `0x0000000a` | Original control word restored; `version` still answered |

These control words describe that board session. The result establishes the
counter-progress requirement for the tested delay path; it does not calibrate
the duration of the delay or establish the timer's absolute frequency. See the
[normal-boot transfer observation](/references/observations/#normal-boot-uart-file-transfer).
