The SD card is the operating-system medium in the M1s Dock storage layout.
It holds Linux and its filesystems; OpenSBI and U-Boot remain in the
[NOR boot chain](/storage/flash/). Kernel maintenance therefore changes SD files
rather than replacing board firmware.

## Planned SD allocation

**Design proposal, not the installed card layout.** Use GPT with five named
partitions: BOOTCTRL, LINUX_A, LINUX_B, DEBIAN_ROOT and RAW. Kernel slots A/B
share one Debian root filesystem. Keep OpenSBI and U-Boot in NOR. The recorded
card instead used MBR/FAT32, and the native Linux tests below used RAM initramfs.

### Boot sectors and partition contract

The SD boot sector is storage metadata, not another copy of the NOR boot
chain. The chip boots from NOR; its U-Boot must understand the SD layout.
Use 512-byte sectors, 1 MiB partition alignment and the following order:

| Location | Size / format | Owner and purpose |
| --- | --- | --- |
| LBA 0 | 512 bytes, protective MBR | Identify the disk as GPT; no executable SD boot stage |
| LBA 1 and 2–33 | Primary GPT header and 128-entry array | Partition names, type GUIDs and per-partition UUIDs |
| Up to byte 1 MiB | Reserved front alignment | No kernel, control record or RAW payload here |
| p1 `BOOTCTRL` | 4 MiB, unformatted | Redundant boot-selection records; distinct from application RAW |
| p2 `LINUX_A` | 256 MiB, FAT32 | Kernel A, DTB, optional small initramfs, integrity manifest |
| p3 `LINUX_B` | 256 MiB, FAT32 | Kernel B with the same file contract |
| p4 `DEBIAN_ROOT` | Capacity policy below, ext4 | Shared Debian rootfs, both kernels’ modules, ordinary user files |
| p5 `RAW` | Remaining aligned usable space, unformatted | Application-defined binary storage, never mounted as a filesystem |
| Physical card tail | At least 1 MiB reserved | Alignment slack, backup GPT entry array and final-sector header |

Provision FAT slots with the GPT Basic Data type
`ebd0a0a2-b9e5-4433-87c0-68b6b72699c7`, and Debian root with Linux filesystem
type `0fc63daf-8483-4772-8e79-3d69d8477de4`. Reserve project-specific type GUIDs
`cc6fbb10-9b4c-4fb0-89ed-d8c9f5646701` for BOOTCTRL and
`cc6fbb10-9b4c-4fb0-89ed-d8c9f5646702` for RAW; these are proposed project
identifiers, not standard types. Give every partition its own unique PARTUUID
at provisioning. Discover it by type/name, then retain its PARTUUID in the
installation manifest. Partition numbers document order; consumers must not
silently select a different disk’s equally named partition.

GPT support does not require an EFI executable or an EFI System Partition.
The proposed design uses U-Boot’s filesystem reads and the board’s Linux
handoff. U-Boot documents [GPT descriptors and type GUIDs](https://docs.u-boot.org/en/latest/usage/cmd/gpt.html)
and [partition-boundary queries](https://docs.u-boot.org/en/latest/usage/cmd/part.html).

### Capacity policy

Use the **measured sector count**, not the card label, when provisioning.
For total bytes `C = sector_count × 512`, calculate:

```text
MiB = 1,048,576 bytes; GiB = 1,073,741,824 bytes
usable_end  = floor((C - MiB) / MiB) × MiB       # exclusive; reserve card tail
root_start  = (1 + 4 + 256 + 256) × MiB         # 517 MiB
remaining   = usable_end - root_start
root_size   = min(16 GiB, floor(0.75 × remaining / GiB) × GiB)
raw_start   = root_start + root_size
raw_size    = usable_end - raw_start
```

The default examples target **8 GB cards and larger, through 2 TiB**, within
the current M0 path’s 32-bit LBA space. A card sold as 8 GB may report a slightly
different capacity; judge its measured geometry. Require at least 4 GiB rootfs
and 1 GiB RAW. Reject an
undersized card; do not silently shrink kernel slots or overlap the tail.
On smaller cards, allocate roughly three quarters of the post-slot capacity
to Debian, rounded down to whole GiB. Cap rootfs at 16 GiB so larger cards
add RAW capacity without moving the earlier partition starts.

For a nominal **128 GB** card, the design uses **16 GiB Debian rootfs** and
approximately **102.70 GiB RAW**. RAW begins at **16,901 MiB**
(`17,721,982,976` bytes, LBA `34,613,248`); its end comes from the measured
card capacity. A 128 GB label is about 119.21 GiB, not 128 GiB.

This is the default binary-storage profile, not a claim that Debian needs
16 GiB. Ordinary documents and packages use ext4; RAW is reserved for consumers
that need block storage. Adjust the 16 GiB cap before provisioning if normal
files need more space. Changing that cap later moves the RAW boundary and
requires backing up and recreating affected partitions. Never automatically
resize an existing installation when a different-capacity card is detected.

### A/B kernel update and recovery

Each FAT slot holds `/Image.gz`, `/board.dtb`, optional `/initramfs.gz`, and
`/manifest.json` with kernel release, file lengths and SHA-256 hashes. The
loader must enforce RAM loading/decompression bounds as well as the FAT slot
capacity. A 256 MiB slot does not imply that a 256 MiB image can run in 64 MiB
RAM. Use the shared root through `root=PARTUUID=… rootwait`; the matching SDH,
partition and ext4 support must be built into the kernel or the small initramfs.

1. Keep the confirmed slot unchanged. Write the candidate’s matching modules
   into `/lib/modules/<release>/` on Debian root, then populate the inactive
   FAT slot. Keep the previous kernel’s modules. Distinct kernel builds must
   use distinct release strings so a candidate cannot replace fallback modules.
2. Flush writes, independently read back the files and verify their manifest
   before publishing a pending slot. Failed staging leaves the confirmed slot
   selected.
3. BOOTCTRL holds two 4 KiB records at partition-relative offsets 0 and 1 MiB.
   Records carry a magic/version, monotonically increasing sequence number,
   confirmed slot, optional pending slot, remaining attempts and CRC32. Update
   the older record, flush, then read it back. Select the newest valid record;
   a torn write must leave the other valid copy usable. CRC detects corruption,
   not authenticity.
4. Allow three candidate attempts. Persist the decremented count **before**
   entering the candidate, and arm a hardware watchdog so a hung kernel causes
   a retry. A load/hash failure immediately selects the confirmed slot; an
   exhausted attempt count clears pending and returns to confirmed.
5. Linux marks the pending slot confirmed only after mounting the expected
   rootfs, checking its release/modules, reaching required userspace services
   and verifying SD reads. Write a new valid control record to confirm it.
   A displayed kernel banner alone is not success.

Provision a valid record with A confirmed after installation verification.
If both BOOTCTRL records are invalid, or both boot slots fail, stop at the
U-Boot recovery console; provide a manual slot choice rather than guessing
which corrupted state was intended. The boot-selection logic belongs to the
NOR U-Boot build so a damaged shared SD script cannot disable both slots.

This is **kernel A/B**, not whole-system A/B. An `apt` upgrade, incompatible
module replacement or corruption of the shared Debian rootfs affects both
slots. Whole-rootfs rollback would require separate rootfs A/B or another
explicit snapshot design. U-Boot’s documented
[boot-count mechanism](https://docs.u-boot.org/en/latest/api/bootcount.html)
provides retry primitives; the redundant BOOTCTRL protocol above is a proposed
integration and has not been implemented or power-loss tested here.

### Debian rootfs target

Prepare a minimal `riscv64` Debian userland on a host and copy it to ext4; use
the board-specific kernel and DTB in the selected FAT slot. The generic Debian
installer and stock kernel are not established BL808 boot paths. Debian’s
[published headless installation guidance](https://www.debian.org/releases/trixie/riscv64/ch03s04.en.html)
lists 512 MB minimum RAM, above this board’s 64 MiB. Thus the minimal userland,
init/services and package-management memory demand remain bring-up work, not
a claim of a validated Debian system. Keep initramfs compact and measure
runtime memory before enabling additional services. No swap partition or
automatic swap use of RAW is assigned by this layout.

### RAW region ownership and format

RAW is a named GPT partition, **not** an unpartitioned tail or free filesystem
clusters. Treat it as opaque application storage: binary captures, log records
or another explicitly defined block format. Normal user files remain on ext4.
The initial installation reserves RAW without formatting it; no payload writer
is enabled until the application chooses its on-disk format.

- Open the verified partition by PARTUUID. Discover `raw_start_lba` and
  `raw_block_count` from its GPT entry. Convert a partition-relative block `r`
  to disk LBA `raw_start_lba + r` only after checking the requested range fits.
  Use 64-bit arithmetic, then enforce the transport’s 32-bit LBA limit.
- Reserve the first and last 1 MiB **inside RAW** for future redundant format
  metadata. Application payload starts at relative 1 MiB and ends 1 MiB before
  the partition end. Payload format, record size, checksums and retention are
  application-defined; consumers must reject an unknown magic/version rather
  than treating unknown bytes as an empty log.
- Use partition-relative offsets in any future format metadata. Extra space
  on a larger card increases the payload capacity; it does not move control,
  A/B or Debian partitions once the 16 GiB rootfs cap is reached. Copying an
  installation to another-size card still requires deliberate GPT/tail repair
  and capacity checks; it is not an automatic expansion operation.
- Linux and M0 must have one controller owner at a time. The current M0 path
  holds D0 stopped for block transfers; it does not coordinate with a running
  Debian rootfs. Use it only while the OS is stopped and filesystems are cleanly
  quiesced. A dedicated RAW partition does not make simultaneous SDH access safe.

### Compatibility and implementation status

This change documents and calculates the design; it does not repartition a
card, change firmware or enable automatic slot switching.

| Component | Current inspected behavior | Needed before using this design |
| --- | --- | --- |
| U-Boot | DOS/MBR, FAT reads/writes; `CONFIG_ENV_IS_NOWHERE`; no GPT or bootcount enabled | GPT reader (`CONFIG_EFI_PARTITION`), partition queries (`CONFIG_CMD_PART`), manifest validation and bounded image loads, redundant BOOTCTRL reader/writer, watchdog and fallback policy; `CONFIG_CMD_GPT` if provisioning/verifying in U-Boot |
| Linux | Diagnostic initramfs; GPT parsing enabled, ext4 not enabled in the inspected image | Early SDH/IRQ/clock support, ext4 support, PARTUUID root selection, minimal Debian startup and confirmation service |
| Host FAT inspector | Exactly one MBR FAT32 partition | GPT-aware explicit slot selection; the existing single-FAT assumption rejects this layout |
| M0/host raw transport | Capacity-bounded block access; no GPT partition policy | Validate selected RAW partition bounds as well as whole-card bounds; do not reuse unrestricted whole-card writes as a RAW-only API |

Before adopting it, verify GPT discovery and both FAT slots, boot each kernel
with matching modules, interrupt inactive-slot and BOOTCTRL updates at each
write boundary, exhaust three failed attempts, exercise watchdog recovery,
test undersized/different-capacity cards and prove RAW first/last-block writes
preserve neighboring Debian and backup-GPT sectors. Existing readback tests
below validate the recorded SDH behavior, not these future A/B guarantees.

## Operating-system contents

| SD contents | Consumer | Role |
| --- | --- | --- |
| Versioned kernel image | U-Boot, then the CPU | Linux executable loaded into PSRAM |
| Linux DTB | Linux, passed by U-Boot | Hardware description selected with the kernel |
| Initramfs, when used | Linux | Initial userspace and early root-filesystem setup |
| Boot configuration | U-Boot | Kernel, DTB, initramfs and command-line selection |
| Root filesystem | Linux | OS packages, configuration and user files |
| `/lib/modules/<version>/` | Linux | Modules matching the selected kernel |

A versioned file layout keeps kernel generations separate:

```text
/boot/
  vmlinuz-<version>
  initrd.img-<version>          (when used)
  dtbs/<version>/<board>.dtb
/lib/modules/<version>/
```

These are paths in the OS installation, not raw card offsets. A separate FAT
boot partition can expose the boot files to U-Boot while Linux mounts its root
filesystem from another partition. The kernel image's format, the boot-file
paths and the boot configuration must agree with the installed U-Boot build.

When changing kernels, keep the matching Linux DTB and modules together, and
retain the previous generation's files and boot selection. The boot-firmware
DTB in NOR has a different consumer and update boundary; see
[two device-tree roles](/storage/overview/#keep-the-two-device-trees-distinct).

## SDH and pad setup

The SD host controller occupies `[0x20060000, 0x20061000)`. The board's SDH pad
configuration uses GPIO0–5. In the recorded U-Boot card-read sessions, selecting
the SDH function with pull-ups allowed card identification and repeatable FAT
file reads. Increasing drive strength without the pull-ups did not establish
the same result.

A configured source clock and a requested card-bus mode are different from a
measured wire frequency. In the 2026-10-20 U-Boot session, the card identified
as SD High Speed 50 MHz; the controller source/divider settings corresponded
to a nominal 48 MHz bus. The later native Linux tests below used a one-bit
bus at substantially lower register-derived card clocks.

## Initial clocks and first CMD8

The 2026-10-23 warm-POR tests identified a missing initialization-clock
operation in the local SDH glue. Enabling SDCLK and waiting 10 ms did not
establish a successful first CMD8. Explicitly starting the vendor pad-clock
generator and waiting for fresh completion did. The card remained powered
between trials; no U-Boot MMC command preceded the probe after each POR.

| Initialization at the same requested card clock | First CMD8 successes |
| --- | --- |
| Previous sequence, 100 kHz | 0/2 |
| Generate 80 initialization clocks, 100 kHz | 2/2 |
| Previous sequence, 400 kHz | 0/5 |
| Generate 80 initialization clocks, 400 kHz | 5/5 |
| Configure the generator but do not start it, 400 kHz | 0/1 |
| Generate 1 initialization clock, 400 kHz | 0/1 |
| Generate 74 initialization clocks, 400 kHz | 1/1 |

Negative first attempts reported combined SDH status `0x00018000`: command
timeout plus error summary. Successful first attempts reported fresh
command-complete status `0x00000001` and R7 `0x000001aa`. A response-less
CMD0 completion does not show that the card received a valid reset command.

Earlier tests increased software delays up to 1 s and lowered the programmed
card clock from 400 kHz to 10 kHz without fixing the first CMD8. Those tests
checked divider readbacks and command-time scaling; they did not measure
idle clocks at the socket. The generator-trigger and count controls above
separate the effective initialization operation from extra waiting or
register setup alone. They do not establish the exact success threshold
between 1 and 74 clocks.

A separate native Linux comparison used the current base
`a804c5742bff224d4cb4d25dd383554d598be32b`, local platform drivers and a RAM
initramfs. The diagnostic DT disabled SDIO/MMC probing so CMD8 was the first
response-bearing identification command. Before the change, the first CMD8
timed out and two later CMD8 requests succeeded; the card still registered.
After adding 80-clock generation through SDHCI's
`platform_send_init_74_clocks` hook, the first CMD8 succeeded. Five native
unbind/bind cycles also succeeded on their first CMD8.

Fresh file and block reads matched, parent/child IRQ counts advanced and SD
write counters remained zero. The diagnostic logging and SD-only DT
restrictions were excluded from the driver change. The
[board observation](/references/observations/#sdh-initialization-clock-follow-up)
records image identities and the read-verification counts; the
[initialization sequence](/clocks/sequencing/#sdh-initialization-clocks)
identifies the vendor controls. Physical cold power-up, another card and
socket CMD/CLK waveforms remain unmeasured in this comparison.

## Polling and interrupt delivery

The U-Boot MMC stack used polling for card commands and file reads. A separate
D0 supervisor diagnostic established the interrupt route:

```text
SDH → MCU forwarding source 17 → D0 PLIC source 81 → supervisor external trap
```

The forwarding block does not require an M0 CPU interrupt handler to pass this
request to D0. Source 17, PLIC ID 81 and a Linux virtual IRQ are separate
identifiers. See the [SDH delivery path](/interrupts/m0ic/#sdh-delivery-path).

Boot-time U-Boot reads and runtime Linux storage access use different drivers.
The Linux kernel needs its own SDH, interrupt and filesystem support to access
the root filesystem on the card after the handoff.

## Recorded file reads

The 2026-10-20 M1s Dock session used U-Boot
`2023.04-rc2-g15b4a6348b9-dirty`, a DOS-partitioned card and a FAT32 partition
starting at sector 2048. Each file was read twice into PSRAM and checked against
an independently recorded host CRC:

| File | Bytes | CRC32 | Matching reads |
| --- | --- | --- | --- |
| `testfile` | 131072 | `7e8e43c2` | 2 |
| `hello.txt` | 55 | `bdb1a907` | 2 |

The read buffers were `0x51000000` and `0x51040000` in that session. Buffer
addresses belong to the running image's allocation map; check live reservations
before using a load address. The [U-Boot memory observation](/address-space/core-views/#observed-u-boot-allocation)
explains the distinction between board memory capacity and available buffers.

## Native Linux PIO and SDMA

On 2026-10-23, the M1s Dock booted a RAM-loaded Linux
`7.3.0-ga804c5742bff-dirty` with local SDH, forwarding-IRQ and clock drivers.
The root filesystem was an initramfs and no SD filesystem was mounted during
the raw-block write tests. The installed NOR and existing SD boot files
were preserved.

The existing `testfile` supplied a known eight-block data extent. Originals
and the immediately adjacent blocks were backed up to the host before
writing. Each tested length of 1, 3 and 8 blocks underwent pattern write,
fresh direct read, original restoration and fresh original/neighbor checks.
FAT, directory and partition-table sectors were not written.

| Transfer mode | SDH module parent | Verification |
| --- | --- | --- |
| PIO | 96 MHz | All three lengths matched and originals/neighbors were preserved |
| SDMA | 96 MHz | All three lengths matched, including an independent PIO read before PIO restoration |
| SDMA | 95 MHz | Same independent read and restoration checks passed |

Before DMA writes, five fresh direct reads and the 128 KiB file CRC passed.
The transfer-mode register showed `0x0022/0x0032` for PIO and
`0x0023/0x0033` for SDMA during actual requests. Host control selected SDMA
(`0x0f04`); the result was not inferred solely from the probe message.
Both parent and child IRQ counters advanced during the I/O. Subsequent
Linux and unchanged-U-Boot checks retained the original file CRCs above.

The kernel used explicit noncoherent DMA configuration and its enabled
T-Head cache-maintenance support. The tested SDHCI configuration selected
SDMA, even though the capability word advertised ADMA2 as well. These results
cover the recorded one-bit transfers and lengths; ADMA, 64-bit DMA, broad
cache/boundary stress, four-bit operation and high-speed electrical timing
were not validated by these tests.

The [board observation](/references/observations/#native-linux-sdh) records
IRQ counts and data-preservation evidence. The
[GLB description](/clocks/glb/#recorded-sdh-parent-rates) gives the programmed
parents and the resulting card-clock calculations.
