The D0 PLIC occupies an aperture starting at `0xe0000000`. Each source has a priority. Each hart context has an enable bitmap, a priority threshold and a claim/complete register.

## Contexts and delegation

The boot device tree lists machine external cause 11 followed by supervisor external cause 9 for hart 0. OpenSBI maps those entries to context 0 and context 1 respectively. In the tested S-mode peripheral route, context 1 uses the claim/complete register at `0xe0201004`.

For `thead,c900-plic`, OpenSBI also enables supervisor access using bit 0 of the T-HEAD control register at `0xe01ffffc`. This PLIC-specific delegation is separate from CPU interrupt delegation and from PMP permissions.

## Register addressing

Let `B = 0xe0000000`, `s` be a source ID and `c` a context index. The source-0 identifier is reserved.

| Register | Address |
| --- | --- |
| Source priority | `B + 4 × s` |
| Pending word | `B + 0x1000 + 4 × floor(s / 32)` |
| Context enable word | `B + 0x2000 + 0x80 × c + 4 × floor(s / 32)` |
| Context threshold | `B + 0x200000 + 0x1000 × c` |
| Context claim/complete | `B + 0x200004 + 0x1000 × c` |

For a bitmap word, the source's bit is `s % 32`. Source 81 therefore uses word 2, bit 17. The [SDH forwarding path](/interrupts/m0ic/#sdh-delivery-path) exercised this source and the supervisor context.

For hart 0's two connected contexts, the addresses are:

| Context | CPU interrupt | Enable word 0 | Threshold | Claim/complete |
| --- | --- | --- | --- | --- |
| 0 | Machine external, cause 11 | `0xe0002000` | `0xe0200000` | `0xe0200004` |
| 1 | Supervisor external, cause 9 | `0xe0002080` | `0xe0201000` | `0xe0201004` |

Enable windows advance by `0x80` bytes per context. The pending bitmap is a
separate window beginning at `0xe0001000`.

## M1s Dock boot readback

In the paired 2026-10-21 power-on and board-RESET sessions, S-mode code read
the first three enable words of context 0 (`0xe0002000`, `0xe0002004`,
`0xe0002008`) and context 1 (`0xe0002080`, `0xe0002084`, `0xe0002088`).
All six words were zero. Both context thresholds read `0x7`, and `sie` was
zero. These values describe the prompt state before a peripheral-IRQ test,
not the configuration used by the earlier SDH handler.

In separate reads on that build, `md.l` at `0xe0002100` and `0xe0002108`
raised load access faults, with each address reported in `TVAL`. By the
address formula above, these are context 2 enable-word addresses, not
context 1. The successful context-1 reads and these context-2 faults are
different observations. See the [board context](/references/observations/).

## Claim and complete

A read of the claim register returns an enabled pending source ID and atomically claims it. Zero means no source was claimed. A write of the handled ID to the same register completes that claim.

Reading claim/complete is an operation with side effects, not passive inspection. Raising a threshold suppresses notifications; it does not make a claim read a harmless status query. A source must have a priority strictly greater than the threshold to notify the target context.

The peripheral and any intermediate latch must be handled before completing a level request that would otherwise remain asserted. The actual trigger type and handler policy belong to the source and controller binding.

## Device-tree interface

The Linux binding for `thead,c900-plic` requires two interrupt cells: source ID and trigger flags. The PLIC's `interrupts-extended` entries identify the CPU-local context connections; they are not peripheral source declarations.

A source count of 82 describes IDs 1 through 82. A driver message reporting 83 mapped entries includes the reserved ID-0 slot; it does not establish a peripheral source 83.
